# Общие правила изменения кода

Этот файл обязателен для имплементера и сабагента, когда их задача разрешает
изменять product-код, тесты или tooling. Процесс роли задают `IMPLEMENTER.md` и
`SUBAGENT.md`; этот документ задаёт только универсальные правила самих правок.

## Scope и качество diff

- Сохраняй чужие незакоммиченные изменения и не включай их в свои коммиты.
- Не делай несвязанный cosmetic refactor, массовое переименование или
  форматирование файлов вне scope задачи.
- Обновляй все затронутые interfaces и call sites; не оставляй параллельный
  mutable owner или временный compatibility path без явного срока удаления.
- Код должен оставаться наглядным без заметной цены в hot path: ясность не
  оправдывает скрытую аллокацию или лишнюю работу на каждом opcode/call.
- Для Zig-facing кода используй актуальные нативные Zig API; не обходи изменения
  stdlib через libc, если Zig предоставляет нужный интерфейс.

## Комментарии

- Комментарий объясняет действующий owner, lifetime, порядок и invariant,
  особенно для GC-visible ownership, publication/rollback, continuation state
  и нетривиального fast path.
- Не указывай в product-комментарии номер фазы, этапа, review, finding или
  историческую причину изменения. История принадлежит git, `report.md` и
  `STATUS.md`.
- Не комментируй пустоту или отсутствие уже удалённого механизма: после удаления
  кода не оставляй `no legacy path`, `field removed`, `nothing to restore` и
  подобные следы. Комментарий допустим только если отсутствие действия само
  является действующим нетривиальным контрактом и без него код будет понят
  неверно; тогда формулируй сам invariant, а не историю удаления.
- Не оставляй закомментированный код и комментарии вместо удалённого кода.
- Не пересказывай очевидную операцию. Объясняй только то, что нельзя надёжно
  вывести из типов, имён и локального control flow.

Плохо:

```zig
// A1.1 Stage 3: the old parked stack is gone, so there is nothing to restore.
```

Хорошо, если этот факт действительно нужен читателю:

```zig
// The base frame remains the thread's stable API anchor across an unwind.
```

## Tests и диагностика

- Тест доказывает семантический класс, а не имя файла, чанка, функции или
  конкретную строку реализации.
- Не компенсируй product-дефект ручной очисткой production state в тесте.
- Временная диагностика default-off, не участвует в runtime-ветвлении и
  удаляется до завершения этапа.

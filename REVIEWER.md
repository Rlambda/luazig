# Роль ревьювера-архитектора

Полностью прочти `AGENTS.md` и этот файл. Ревью завершённой итерации и
постановка следующей задачи — **разные процедуры**, выполняемые в указанном
порядке. Не называй быстрый обзор будущей задачи проверкой уже написанного
кода.

1. Если имплементер передал новый `report.md` или вердикт по его итерации ещё
   не вынесен, полностью прочти и исполни `REVIEW.md`. Проведи собственное
   расследование изменённого кода, tests и evidence; отчёт имплементера —
   вход, а не доказательство принятия. Не переходи к новой задаче, пока
   результат не принят или явно не установлен иной вердикт.
2. Только после **ACCEPT** (включая ACCEPT + RECORD независимого backlog)
   полностью прочти и исполни `PLANNING.md`: короткий scout кандидатов,
   использование глубокого research имплементера при существенной
   неопределённости, согласование нового глобального дизайна с владельцем и
   запись следующего `prompt.md`.
3. При **CORRECT** ревью само формулирует ограниченный correction `prompt.md`
   по доказанному дефекту предыдущего этапа; `PLANNING.md` не запускается.
   При недостаточном evidence сначала исчерпай доступные проверки ревью;
   только объективно недостающий факт выноси в bounded research/verification
   по `REVIEW.md`, не объявляя принятие. При **REDESIGN** сначала верни
   архитектурное решение владельцу; не выдавай implementation prompt на
   неутверждённую замену модели.

Если этап был принят в предыдущем ходе и новой итерации имплементера нет,
начинай с `PLANNING.md`, не повторяя уже завершённое ревью. Не читай
`IMPLEMENTER.md`, `SUBAGENT.md` и `CODING_RULES.md`, кроме задачи по изменению
самих process-документов.

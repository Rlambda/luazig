# P16.0 — Количественная модель производительности vs PUC Lua 5.5

> Дата: 2026-08-25. Инструменты: `perf_compare.py --counters` (perf stat -j,
> median-of-3, core 0), `perf_profile.py` (perf record --call-graph lbr),
> VmStats (`--stats` / `T.stats()`, P16.0b), PUC instruction counts via
> count-hook на идентичных телах microbench (`/tmp/mb_count.lua`-метод:
> bench() обёрнут hook'ом каждые 100k инструкций). Все счётчики сняты на
> одних и тех же телах workloads — числа сопоставимы напрямую.

## Найденные механизмы (по данным, не гипотезы)

### F1 — MMBIN/MMBINI/MMBINK исполняются безусловно (главный источник instrX 1.5x)
PUC 5.5 `op_arith_aux` (lvm.c:992-998): на fast path делает `pc++` —
**пропускает** следующую MMBIN-инструкцию. luazig диспетчеризует её как
no-op (vm.zig `.mmbin, .mmbini, .mmbink => {}`): int_arith исполняет
mmbin 50.5M раз при 50.5M ADD — +1 инструкция на КАЖДУЮ арифметику.
Этим объясняется instrX 1.52–1.57 у int/float/mixed/branch/hash/array.
Фикс: pc-skip на fast path в арифметических opcodes (точная семантика
PUC: skip только при успехе; на failure MMBIN исполняется и зовёт
метаметод). Проверяется гистограммой (mmbin → 0 на int-коде).

### F2 — SETTABUP проваливается в rawSet (field_access costX 2.77)
`.setfield` (vm.zig:11267) имеет inline-апдейт (nodeLookup → присваивание),
`.settabup` (vm.zig:11018) — нет: `try self.rawSet(env.Table, key, val)`
на каждый сет. field_access: 10.1M сетов → rawSet 30.2% в профиле +
Node.keyMatches 8.8% (второй lookup уже внутри rawSet). Фикс: тот же
inline-апдейт для SETTABUP (и проверить SETI/SETTABLE на ту же болезнь).

### F3 — Аллокатор/хеш доминируют table-construction (temp_table costX 3.14 при instrX 1.03)
Профиль temp_table_alloc: Wyhash.final 13.1% + SmpAllocator free/alloc
22.7% + string-intern 5.3%. Вопрос для расследования: почему конструктор
`{1,2,3}` (NEWTABLE+SETLIST, array-part) вообще хеширует? Плюс RSS
88–103MB vs 15.9MB у PUC — GC pacing не срезает пик под burst-аллокацией.
Это P16.4-материал (allocator A/B + GC pacing), не bytecode.

### F4 — Call-механизм = 39% вне dispatch (lua_calls costX 2.99 при instrX 1.16)
Профиль: completeBytecodeExecFrame 11.4% + pushBytecodeExecFrame 10.0% +
setPendingCall 9.3% + applyBytecodePendingResults 8.4%. Инфляции почти
нет — цена кадра. Цель P16.2: сверить cost-per-call с PUC precall+
goto startfunc; кандидаты — pending-call bookkeeping и frame init.

### F5 — Coroutine: 2.25x instrX + нативный resume-механизм
VM-инструкций 5.6M vs 2.5M (тело yielder'а раздутее), но и нативно:
compiler_rt.memset 13.9% (save/restore кадров), builtinCoroutineYield/
Resume 16.4%. Цель P16.3 (zero-alloc + меньше memset).

### F6 — Не всё хуже: comparisons instrX 1.21 (fused GEI/LEI дешевле
PUC-цепочки), zig cache-miss% НИЖЕ PUC на hash_access (11.8% vs 50.7% —
32B Node работает); узкое место — dispatch, не память.

## Рекомендация P16.1 (данные vs изначальная гипотеза)

Координатор предполагал table fast paths первыми. Данные корректируют:

1. **P16.1a: MMBIN pc-skip** — самый дешёвый и системный выигрыш:
   убирает ~1/3 инструкций всего арифметического кода (8 из 16 workload'ов
   имеют instrX 1.42–1.57 почти целиком из-за него). Ожидаемый эффект на
   geomean: instrX 1.32 → ~1.1, т.е. slowdown ~2.70 → ~2.3 при том же costX.
   Риск: метаметод-slow-path семантика (тесты: metamethod_add, matrix,
   testC, полный parity gate).
2. **P16.1b: SETTABUP/SETI inline-апдейт** — точечный фикс по образцу
   SETFIELD; бьёт в field_access/global_arith (rawSet 30% профиля).
3. **P16.2: call-механизм** (F4) — после 1a, когда dispatch-доля станет
   относительно больше.
4. **P16.3/P16.4** — coroutine и allocator/GC по F5/F3.
Table GET-пути (изначальная гипотеза P16.1) по данным НЕ главный цель:
get_fast уже инлайнен, cache-miss ниже PUC.

# P16.32 T1 — Allocation decomposition truth (alloc-family divergence)

**Task**: P16.32 T1 (research). Measure allocation COUNT/SIZE truth for the
alloc-family workloads on both sides (zig counting-allocator harness, PUC
LD_PRELOAD malloc counter), attribute each zig allocation to its source,
compare capacities, estimate per-alloc cost, explain the mem.eql/internStr/
rawGet presence, and rank architectural fix candidates by measured
instructions/iter savings.

**Provenance**: measured at git 183983e (P16.31 COMPLETE final), zig 0.16.0.
No production changes survive (A/B patches applied, measured, reverted;
`git status` clean for `src/`). Smoke 71/71 PASS on the final clean rebuild.
Zig harness: counting-allocator forwarder around `std.heap.smp_allocator`,
Vm.init → runBytecode per shape, warmup 500 iters (uncounted), measure window
n iters (counted), per-callsite ret_addr histogram symbolized via addr2line.
PUC: LD_PRELOAD shim counting malloc/calloc/realloc/free + size histogram,
two-run differencing (N=250000 vs 2N) with fixed 1000-iter warmup so startup
costs cancel exactly. PUC binary: build/lua-c/lua (Lua 5.5.0).

## 2. Answers to the task questions

### Q1 — does zig allocate MORE times per iteration?

**Only for metamethod_add: 4 vs 2.** All other shapes have EQUAL counts
(2/2, 2/2, 1/1, 0/0, 2/2). The two extra metamethod_add allocations are
call-machinery, not table-model:
1. `opTailcall` .Builtin branch dupes builtin results into a heap slice
   (16B = 1 Value) before finishing the tailcall (vm.zig:17666).
2. `opTailcall` → `beginBytecodeClose` allocates an 80B
   BytecodeCloseContinuation per tailcall even when there is nothing to
   close (no TBC marks, no open upvalues) (vm.zig:8154/17704). PUC OP_TAILCALL
   replaces the CallInfo in place (luaD_pretailcall); it never allocates and
   never runs close machinery (k-flag gates luaF_closeupval only).

### Q2 — initial capacities

**Both pre-size exactly; no capacity divergence.**
- PUC `{1,2,3}`: parser counts list fields → OP_NEWTABLE C=3 →
  luaH_resize(t,3,0) → array EXACTLY 3 slots (measured 31B = concretesize(3)).
  `{v=1}`: OP_NEWTABLE b=1 → hash EXACTLY 1 node (measured 24B).
- zig `{1,2,3}`: NEWTABLE asize hint 3 → tableResize(3,0) → array EXACTLY 3
  (measured 48B = 3×Value16). `{v=1}`: hsize_log2=1 → EXACTLY 1 Node
  (measured 32B).
- SETLIST batching identical (both fill the pre-sized array; no rehash).
The byte difference per table is pure struct-model: zig Table 72 vs PUC 48;
zig array slot 16B tagged Value vs PUC 9B tagless+1B tag; zig Node 32 vs
PUC 24. No over-allocation on either side.

### Q3 — per-alloc COST (count equal → cost is the difference?)

Decomposed by A/B measurement (patch → measure → revert):

**Instructions: SmpAllocator ≈ glibc tcache.** After removing the testC
chain (see Q4), temp_table_alloc runs at **1145.3 zig vs 1138.7 PUC i/iter**
— parity, with 2 allocs + 2 frees per iter on BOTH sides. The instruction
cost per SmpAllocator alloc+free pair is ≈ glibc malloc/free. The T0 finding
"87% of alloc symbol samples on the lock cmpxchg" was 87% *of samples inside
SmpAllocator symbols* — SmpAllocator itself is only ~12% of cycles; the lock
stall costs cycles (~8 cycles/alloc+free pair: patched temp_table_alloc
276.6 vs PUC 244.9 cycles/iter = +32 cycles for 2 pairs), not instructions.

**The dominant per-alloc cost was the testC chain** (Q4): ~440 instr per
table allocation, i.e. ~880 instr/iter for 2-alloc workloads — 43% of
temp_table_alloc's total zig instructions.

Measured A/B (instructions/iter, n=500000, perf stat -r 3):

| workload | baseline | −testC chain | −testC −GETFIELD-slowpath | PUC | baseline ratio | final ratio |
|---|---|---|---|---|---|---|
| temp_table_alloc | 2022.3 | **1145.3** | — | 1138.7 | 1.69x | **1.01x** |
| table_alloc_setmetatable | 3004.3 | **2183.1** | — | 1519.5 | 2.00x | 1.44x |
| metamethod_add | 4620.2 | 3828.6 | **3485.5** | 2108.0 | 2.22x | 1.65x |
| metamethod_call_noalloc | 630.3 | 630.3 (no allocs) | 630.2 | 375.6 | 1.68x | 1.68x |

Measured A/B (cycles/iter): temp_table_alloc 409.2→276.6 (PUC 244.9);
table_alloc_setmetatable 690.4→500.6 (PUC 329.9); metamethod_add
1178.4→1020.0 (PUC 478.3; GETFIELD fix not in the cycle run).

So: for temp_table_alloc the ENTIRE 1.69x divergence is the testC chain.
For table_alloc_setmetatable the testC chain is ~40% of the gap; the rest is
builtin-call machinery (pushBuiltinCFrame stack-growth checks + call_frames
addOne + hidden-flag bookkeeping vs PUC's in-place C CallInfo) + 72B Table
init. For metamethod_add the testC chain + GETFIELD slow path leave 1.65x:
extra allocs (Q1) + opTailcall machinery + MMBIN dispatch.

### Q4 — mem.eql / internStr / rawGet in the loops

**Root cause (gdb-proven backtrace, breakpoint on vm.Vm.internStr after
100k hits):**

```
allocTable (vm.zig:7576)
 → testcConsumeAllocCount (vm.zig:7243)
   → getGlobal("T")            ← raw-name lookup, EVERY table allocation
     → getField(global_env, "T")   (vm.zig:30070)
       → internStrAssume("T")      (vm.zig:18525)
         → internStr              ← Wyhash("T") + StringTable lookup
                                    with mem.eql content compare
       + rawGet(global_env, key)   ← the rawGet samples
```

`testcConsumeAllocCount` implements testC's `T._alloccount` memory-fault
injection, but instead of a cached flag it does a FULL global-by-name lookup
(hash the name, string-table content compare, global hash get) on EVERY
`allocTable`/`testcChargeMemory` call — even when the testC module `T` does
not exist at all. Same chain explains internStr+mem.eql in metamethod_add
(2 table allocs/iter → 2 chains) and table_alloc_setmetatable. PUC's ltests
equivalent is compile-time guarded — zero cost in the release lua-c binary.

Secondary mem.eql/rawGet source (metamethod_add only): `a.v`/`b.v` GETFIELD
on metatable'd tables. zig's `.getfield` fast path requires
`metatable == null` (vm.zig:14494), so tables WITH a metatable always take
the slow path (bytecodeGetIndex → tableGetValueDepth → rawGet). PUC's
OP_GETFIELD does `luaV_fastget` = raw hash get FIRST regardless of metatable;
only an empty result consults `__index`. A/B fix (raw-get-first): −343 i/iter
on metamethod_add. `setmetatable` global lookup itself is clean: GETTABUP
uses pre-resolved constants + nodeLookupShortStrIdentity (pointer identity).

### Q5 — GC pacing contribution

- **PUC**: GCdebt starts 0 (lstate.c:373) → the first luaC_step fires during
  state init/openlibs; thereafter threshold = PAUSE(200%)×marked → cycles
  run constantly, scaled to the (tiny) live heap. Measured frees/iter ==
  allocs/iter in steady state.
- **zig**: `gc_auto_threshold_kb` starts at **32768 (32MB!)** (vm.zig:3995) —
  the first automatic cycle fires only when gc_count_kb ≥ 32MB. Below that,
  NO GC cycle runs at all (verified: at n=200000 = 24MB accumulated, 0 table
  frees; at n=500000 = 60MB, frees ≈ allocs — GC kicks in mid-run).
  Consequences: (a) short runs never collect (memory accumulates until
  vm.deinit); (b) in the 500k-iter microbench window the first ~half runs
  GC-free (a zig ADVANTAGE), then does catch-up collection. Not a per-iter
  cost driver in these workloads, but a pacing divergence from PUC worth a
  dedicated look (PUC's first-cycle-immediately + 2×live threshold).
- `gcRegisterObject` per table creation is an amortized ArrayList append
  (occasional growth realloc, 38064B seen once per run) — minor.
- metamethod_call_noalloc profile shows gcMarkBytecodeProto/gcPropagateOne
  (GC marking of the __add proto during cycles) and Wyhash.hash — GC mark
  work + hash recomputation worth a T2 look, out of T1 scope.

## 3. Ranked architectural candidates (measured expected savings)

1. **Cache the testC alloc-count check** — replace the per-alloc
   `getGlobal("T")`-by-name chain in `testcConsumeAllocCount`/
   `testcChargeMemory` with a VM-level flag (set when the `T` module is
   registered / when `T._alloccount` is written; the flag short-circuits the
   whole chain when testC is inactive — the production default).
   PUC-faithful: ltests hooks are compile-time guarded in release builds.
   **Measured: −877 i/iter temp_table_alloc (1.69x→1.01x),
   −821 i/iter table_alloc_setmetatable (2.00x→1.44x),
   −792 i/iter metamethod_add; cycles −32%/−27%/−13%.**
   Semantics preserved: the flag must be invalidated on T creation,
   T._alloccount writes, and setglobal("T", nil).
2. **GETFIELD/SETFIELD raw-get-first (PUC luaV_fastget semantics)** — drop
   the `metatable == null` precondition; do the pointer-identity hash get
   first, consult metamethods only on empty/miss (mirror of PUC OP_GETFIELD/
   OP_SETFIELD). **Measured: −343 i/iter metamethod_add** (2 GETFIELDs/iter
   on mt'd tables); also helps any __index-less metatable read pattern
   (getmetatable-carrying objects are common: strings, boxed values).
3. **opTailcall: nothing-to-close fast path** — skip the 80B
   BytecodeCloseContinuation allocation (and the pending-call dance) when
   the frame has no TBC marks and no open upvalues (PUC OP_TAILCALL replaces
   the frame in place; close machinery runs only via the k-flag
   luaF_closeupval). Saves 1 alloc + 1 free per tailcall-to-builtin.
   **Estimated: ~1 SmpAllocator alloc+free pair + continuation
   create/destroy ≈ 100–200 i/iter + ~20–40 cycles/iter on metamethod_add**
   (not separately A/B-measured; bounded by the metamethod_add remaining
   gap).
4. **opTailcall .Builtin branch: avoid the results dupe** — the 16B
   `alloc.dupe(Value, outs)` exists because `outs` is a stack slice that the
   completion must own. If the nothing-to-close fast path (3) returns
   results directly to the pending-call completion without an owning copy
   (PUC moves results on the shared stack), the dupe disappears. Saves 1
   alloc + 1 free per tailcall-to-builtin. Same estimate class as (3);
   together (3)+(4) remove BOTH extra metamethod_add allocations, reaching
   alloc-count parity with PUC (2/iter).
5. **Builtin call machinery (pushBuiltinCFrame)** — remaining
   table_alloc_setmetatable gap after (1): 664 i/iter vs PUC. PUC's C call
   pushes a CallInfo in place on the same stack; zig grows/checks bc_stack +
   bc_boxed, appends to call_frames ArrayList, sets flags. A preallocated
   C-frame slot / branch-free growth check could cut a large part. Needs its
   own T2 decomposition (not A/B-measured here).
6. **GC initial threshold 32MB → PUC pacing** (correctness/parity more than
   perf: zig currently does LESS GC work than PUC in these windows). Align
   initial debt/threshold semantics with PUC (first cycle immediate,
   threshold = PAUSE%×marked). Perf-neutral-to-negative for these
   workloads; listed for parity completeness.

Not candidates (measured equal): allocation COUNTS (except metamethod_add),
initial capacities (both exact), setmetatable cost (0 allocs both).

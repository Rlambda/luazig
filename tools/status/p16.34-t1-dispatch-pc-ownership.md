# P16.34 T1/Cut 1 — dispatch_pc ownership inventory (pre-patch truth)

Mandatory T1.1 inventory for removing the per-opcode `self.dispatch_pc = ctx.pc`
store (vm.zig:14247) and migrating to PUC `savestate` ownership: the pc is
published ONLY at semantic boundaries.

## 1. PUC 5.5 reference model (lua-5.5.0/src/lvm.c)

- `savepc(ci)` = `ci->u.l.savedpc = pc` (lvm.c:1144) — publish to the heap
  CallInfo. **No per-fetch store anywhere** — the loop head (vmfetch) never
  publishes.
- `Protect(exp)` = `(savestate(L,ci), exp, updatetrap(ci))` (lvm.c:1158) —
  savestate BEFORE every error-capable operation (MMBIN/MMBINI/MMBANK
  `luaT_trybinTM`, comparisons `op_order`/`op_orderI` slow paths, SETTABUP/
  SETTABLE/SETFIELD `luaV_finishset`, OP_FORPREP ("in case of errors",
  lvm.c:1851), OP_CLOSE `luaF_close`, OP_UNM/OP_LEN ...).
- `checkGC(L,c)` = `luaC_condGC(L, (savepc(ci), L->top.p = c), ...)` (lvm.c:1178)
  — savepc is the `p` argument of luaC_condGC, evaluated ONLY when
  `GCdebt > 0` (a GC step will actually run) — **conditional publication**.
- Error location: luaG_runerror → luaG_addinfo reads `ci->u.l.savedpc` — the
  LAST PUBLISHED value; every error site inside luaV_execute is under Protect.
- PUC's GC does not read savedpc for stack liveness (marks to `L->top`);
  luazig's gcClearDeadFrameRegisters/live_reg_top[pc] does — that is why
  luazig needs a fresh pc at every GC-step entry from dispatch.

## 4. Field fate

`dispatch_pc` (vm.zig:4162) is DELETED: after §2–§3 no reader remains. The
heap CallFrame `u.lua.pc` (published by parkActiveFrame) is the single
savestate, exactly PUC's `ci->u.l.savedpc`.

## 5. Correctness argument (the T1 critical question)

"Can a GC/allocation happen INSIDE an opcode handler WITHOUT passing a parking
site, such that syncTopFrameForGc would read a stale pc → live_reg_top[pc]
wrong → GC clears live registers?" — After the cut: NO. The only GC-step
entries from dispatch are condGcFromDispatch (publishes) and allocTable's GC
branch (publishes when ctx != null; the only dispatch caller passes ctx).
Every fail() site reachable with the active dispatch frame on top publishes
first (§3.1/3.2); fail() from a C frame reads the parent parked at the CALL
(already the value dispatch_pc carried there — per-fetch store agreed with the
park at every such site, so behavior is unchanged). Nested dispatch loops
(builtin → lua_call → child runBytecodeDispatch) each publish at their own
boundaries; a parent never reads a child's publication because the parent
re-publishes at every one of its own fail/GC/push sites.

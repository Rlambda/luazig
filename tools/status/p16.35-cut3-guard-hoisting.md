# P16.35 Cut 3 — builtin OP_CALL guard-chain hoisting (2026-09-10)

**Provenance**: HEAD `d518ce1` (src == `be4fb0a` state, P16.35 Cut 1
reverted). Implements ranked mechanism #2 from
`p16.35-t5-coroutine-decomposition.md` (guard-chain ceremony, ~230 i/it
estimated on coroutine_yield, 15% of its transition gap).

## What was cut

Every builtin (non-closure) OP_CALL paid an ask-then-decline prologue chain
that PUC's OP_CALL (lvm.c:1720-1732: savepc + luaD_precall + updatetrap;
precallC ldo.c:642-659: checkstackp + prepCallInfo + 2-i hookmask read)
does not have. Three hoists, all generic id-class/flag gates — no
benchmark special cases, no new flags, no semantic changes:

1. **Protected-family id gate hoisted to the caller** (OP_CALL vm.zig
   `opCall` + OP_TAILCALL `opTailCall`, both sites): `tryPushBytecodeProtectedCall`
   is now called only when `id == .pcall or id == .xpcall`. Previously every
   builtin paid the out-of-line call (22 i incl. the ArrayListUnmanaged
   init + defer-deinit that runs even on the `id != .pcall/.xpcall` early
   return at vm.zig:12172-pre). The internal id check is kept — the
   function stays self-contained.
2. **Coroutine-switch trampoline flag hoisted to the caller** (same two
   sites): `tryRequestBytecodeCoroutineSwitch` is now called only when
   `self.bytecode_coroutine_trampoline_active` (its own first check,
   vm.zig:10453-pre; false in the steady state). One load+test replaces
   the 20-i out-of-line early-return call for every non-trampoline call.
3. **Return-event hook probes gated at the call site** (opCall builtin
   epilogue): `tryPushBytecodeDebugHook` + `dispatchBytecodeHookWithCallee`
   are wrapped in `if (self.hooks_active_cached)` — the identical first
   check inside both helpers (PUC precallC reads L->hookmask directly,
   ldo.c:650). No hooks → no out-of-line probe, no call-arg staging.
4. **builtinOutLen comptime table**: the ~90-case out-of-line switch
   (23 i per call: call overhead + jump-table dispatch to fetch a
   constant) is split into `builtin_const_out_len` (comptime `?u16`
   table, default 1 = old `else => 1`, null = dynamic) + inline
   `builtinOutLen` wrapper (one direct table load at each of the 5 call
   sites) + out-of-line `builtinOutLenDynamic` (only the 10
   argument-dependent cases: io_lines, io_lines_iter, assert, select,
   string_byte, string_find, string_match, utf8_codepoint, string_unpack,
   table_unpack). Single source of truth contract documented on the
   table: fixed → table, dynamic → null + switch case; a missing case
   degrades to default 1 (truncated results, test-visible).

`coroutineBuiltinFastPathEligible` (task item c) was audited: already
gated by `(id == .coroutine_resume or id == .coroutine_yield)` at both
call sites (the `co_fast_path` conditions) — its 69 i/cycle is paid only
by the coroutine builtins themselves; that is mechanism #4
(O(frames) yield-boundary derivation), out of this cut's scope.

## GC placement: KEPT (documented decision)

The task's step 1 (move the OP_CALL-path GC check to allocation sites,
PUC parity) was investigated and **deliberately not taken**:

- PUC runs checkGC ONLY at allocation opcodes (lvm.c:1425 OP_NEWTABLE,
  1631 OP_CONCAT, 1933 OP_CLOSURE) and inside object-creating C API
  functions — luaC_checkGC in lapi.c lua_tolstring:426,
  lua_pushlstring:549, lua_pushexternalstring:564, lua_pushstring:581,
  lua_pushvfstring:592, lua_pushfstring:603, lua_createtable:800,
  lua_concat:1299, lua_newuserdatauv:1360 — never at OP_CALL.
- luazig's OP_CALL epilogue `condGcFromDispatch` (vm.zig:18703) is the
  ONLY GC trigger for builtin-string-allocating loops: `internStr` (the
  chokepoint of ALL string creation) has no GC check, while `allocTable`
  does (vm.zig:7738). Removing the epilogue check without adding
  string-site checks would diverge from PUC: a `tostring`/`string.format`
  loop would grow the heap unboundedly where PUC bounds it via the lapi.c
  checks (GCdebt crosses zero inside the C function's own push).
- The PUC-faithful relocation — a GC check at string-creation sites
  mirroring luaC_checkGC in PUC's push APIs — requires `internStr` to be
  able to step GC (DispatchError: finalizers/__gc can raise), i.e. a
  signature cascade across the entire string-creation surface (parser,
  error-message paths, stdlib). That is a dedicated architectural cut,
  not a guard hoist; GC pacing is the sensitive parity area
  (gc.lua/tracegc history, vm.zig:25143-25153).
- Controls confirm zero GC pacing change: int_arith, branch_loop,
  temp_table_alloc, lua_calls are **exactly 0.00 i/it** delta
  (instruction-identical), and the GC-sensitive suites (gc, gengc,
  tracegc, locals) are green in the matrix.

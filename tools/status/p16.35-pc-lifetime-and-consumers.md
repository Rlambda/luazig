# P16.35 PC lifetime & consumers — proof that a code cursor is stable for a frame's whole lifetime (2026-09-10)

Question (P16.35 planning): if `ctx.pc` becomes a `[*]const bc.Instruction`
cursor into `proto.code`, is that pointer stable for the entire lifetime of
a CallFrame referencing the proto — including parked (yield-suspended)
coroutines? Measured source 6290951 (src/ byte-identical at HEAD 016532d).

Verdict up front: **YES.** `Proto.code` is an immutable, never-reallocated
slice from the moment the Proto is constructed; the backing bytes are kept
alive by an ownership chain that is provably at least as long as every
CallFrame that references the proto; and Protos are refcounted trees, never
moved by the GC (they are not GC objects — the GC only marks the *closures*
that hold tree references). Each proof leg below cites the exact source.

## 1. Text-compiled protos: `ProtoBuilder.finish` → code is immutable

`ProtoBuilder.finish` (src/lua/bytecode.zig:1210–1291):

- `self.code.toOwnedSlice(alloc)` (bytecode.zig:1214) — the builder's
  ArrayList buffer is *transferred* to the Proto as a `[]const Instruction`
  slice (field decl bytecode.zig:797). `toOwnedSlice` may shrink the
  allocation in place; it never leaves a second alias, and the builder's
  `self.code` is reset to `.empty` (bytecode.zig:1274) so nothing can
  append/resize it afterwards.
- The slice is assigned exactly once, at proto construction
  (bytecode.zig:1241). `Proto` has no `deinit` method (bytecode.zig:899);
  the only code-array free is the structural `destroyProtoTree` at tree
  death.
- Grep for production writes to `.code` after construction: none — the only
  `.code =` sites are `finish` (1241), `undumpProto` (undump.zig:499), and
  unit-test fixtures. `Proto.code` is `[]const` — any mutation would need
  `@constCast`, and the only `@constCast(code)` is the undump error-path
  free (undump.zig:390).

So for text-compiled protos the bytes and their address are fixed from
`finish` until `destroyProtoTree`. A cursor into them is stable.

## 2. Undumped protos: backing-ownership chain for BOTH modes

`UndumpReader.undumpProto` (src/lua/undump.zig:329–520) has two modes,
selected by `luaL_loadbufferx`-style mode `'B'` (vm.zig:26890, PUC
`lundump.c` PF_FIXED parity):

### Fixed mode (`reader.fixed = true`, vm.zig:26955)

`code` (undump.zig:373–381) and `lineinfo` (undump.zig:447+) are BORROWED
directly from the input buffer via `getaddr` (PUC `f->code = getaddr(...)`,
lundump.c:187–193). The proto records `flags.fixed_arrays = true`
(undump.zig:518) so `destroyProtoTree` skips freeing them and
`protoTreeFootprint` excludes them from the GC charge. Who keeps the input
buffer alive for the tree's lifetime — `loadBinaryChunk`
(vm.zig:26977–27003), three input ownership classes:

| input class | backing mechanism | freed by |
|---|---|---|
| `.borrowed` (C buffer, `luaL_loadbufferx('B')`) | caller-owned by contract — "the caller must keep it alive until the closure is dropped and GC'd" (vm.zig:26982–26990); nothing recorded in SourceBacking (P16.16 C6: the never-read span was removed, the contract is documented at the load site) | caller (same contract PUC has) |
| `.owned` (lua_load reader collection with 'B') | `tree.source_backing.extra.owned.append` (vm.zig:26994–26996) — the tree owns the bytes | `destroyProtoTree` at last release |
| `.pinned` (Lua-level `load(string, 'B')`) | `tree.source_backing.addPin` (vm.zig:27001) — the source LuaString is GC-pinned for the tree's lifetime; the GC marks it through `gcMarkBytecodeProto` → `source_backing.pin`/`extra` (vm.zig:25364–25372) | GC/unpin at tree death |

### Non-fixed mode (default binary load)

Nothing is borrowed: `code` is allocated and copied word-by-word
(undump.zig:382–389), `lineinfo` likewise, string constants are interned
into the VM string table via the intern callback, and the remaining debug
lexemes (locvar/upvalue names, function/source names) are CLONED by
`cloneUndumpedStrings` with the copies registered on the tree
(vm.zig:27005–27008, freed with it). An `.owned` input is freed immediately
after undump (vm.zig:27011–27015) — nothing points into it anymore.

In both modes, everything `Proto.code` points at is owned by (or contracted
to) the tree for its full lifetime.

## 3. Proto/tree release vs live CallFrames — the frame can never outlive its proto

Ownership model (CUT2, bytecode.zig:820–902): the root Proto IS the
ownership root. `ref_count` = producing reference + one per Closure.

- **Closure creation retains**: `retainTreeForClosure` (vm.zig:26135) at
  every creation site — the VM-bind boundary (vm.zig:13774), OP_CLOSURE
  (vm.zig:17244), `createClosure` (vm.zig:26235), load paths (26295,
  26352), C API (26653).
- **Closure death releases**: `gcFreeObject` `.closure` arm
  (vm.zig:25009–25027) → `releaseTree`; the LAST release runs the
  one-time `destroyProtoTree` (bytecode.zig:974–979) which frees every
  proto struct and every owned array in the tree. Protos are NOT GC
  objects themselves — they die only through this refcount, only when the
  last closure dies. Nothing ever moves a Proto (no compaction path
  touches them), so `*const bc.Proto` and `proto.code.ptr` addresses are
  stable for the whole tree lifetime.

Now the frame side. A Lua CallFrame references its proto via the raw
pointer `fr.u.lua.proto` (vm.zig:1562) — no refcount of its own. The
lifetime proof rests on the invariant:

> While a CallFrame with `u.lua.proto == P` is live (active on any
> thread's `call_frames`, including parked-suspended coroutines), a
> closure over P's tree is reachable by the GC, so `ref_count ≥ 1`.

Proof legs:

1. **Frame ↔ closure pairing.** Every frame push writes the callee closure
   value at `bc_stack[func_slot]` and takes `u.lua.proto` from that closure
   (`pushBytecodeExecFrame`/`pushStaged`, vm.zig:13063/13267 region); the
   tailcall frame-reuse path rewrites BOTH together — `fr2.u.lua.proto =
   new_proto` + `fr2.func_slot = new_func_slot` with the new callee placed
   there by the TAILCALL stack setup (vm.zig:18004–18013, comment at
   18010: "callee is at bc_stack[func_slot], set by TAILCALL stack setup").
   The function value at `func_slot` is preserved for the frame's whole
   lifetime (vm.zig:1656–1658 — PUC `ci->func` invariant; needed for
   debug.getinfo and result placement). So `frame live ⟹ closure over
   frame's proto is at bc_stack[func_slot]`.

2. **Active thread.** `gcMarkMutableRoots` (vm.zig:23563+) walks every
   frame of the active thread's `call_frames` and marks
   `self.bc_stack[frame.func_slot]` explicitly (vm.zig:23604) — the frame's
   own closure is a GC root by construction.

3. **Parked coroutines.** Parked threads are marked via
   `gcMarkValue(.Thread)` on `wrap_thread` / `current_thread` /
   `forced_close_thread` (vm.zig:23567–23569) plus any thread reachable
   from Lua values; `gcPropagateOne`'s thread traversal walks EVERY frame
   in `th.call_frames` and marks `frame_stack[exec_fr.func_slot]` — the
   callee closure — for each (vm.zig:25722–25726). The register scan is
   bounded by `live_reg_top[pc]` (the heap `u.lua.pc` — see the cursor
   audit's heap-PC inventory), but the callee mark at `func_slot` is
   UNconditional, so a suspended frame's closure survives every GC cycle
   the frame survives.

4. **Pending calls.** Frames with a pending metamethod call also keep
   `pending.callee` marked (vm.zig:25746–25749) — the child closure cannot
   die under a pending call either.

5. **Frame pop ordering.** A frame is popped from `call_frames` only on
   return/error/close paths, and the closure value at `func_slot` is
   consumed (result placement) or overwritten only as part of the same
   unwind — there is no window where the frame is on `call_frames` but its
   `func_slot` no longer holds the closure (the pop-detach invariant for
   TBC, vm.zig:1540–1545, is the same ordering discipline).

Conclusion of §3: an active or parked-suspended CallFrame can NEVER
outlive the proto it references — the frame's own closure pins the tree,
in both the active-thread root walk and the parked-thread propagation
walk. `destroyProtoTree` (which frees `code`) is unreachable while any
such frame exists.

## 4. Conclusion — cursor stability verdict

A `[*]const bc.Instruction` cursor derived from `proto.code` (either
representation: raw many-pointer, or slice-iterator pair) is stable for
the whole frame lifetime, including across coroutine yield/resume and
including undumped fixed-buffer protos, because:

1. `Proto.code`'s bytes and base address are immutable from construction
   (§1, §2) — no realloc, no mutation, no compaction;
2. the backing ownership (owned slice / tree-owned buffer / GC-pinned
   string / caller contract) covers the tree's entire lifetime (§2);
3. the tree outlives every frame referencing it, active or parked (§3);
4. the only events that invalidate a cursor — tree death — require the
   frame to be gone first.

The one representation caveat (not a lifetime issue): the heap-published
`u.lua.pc` must remain an index (or become `cur - code.ptr` at publish)
because the compact u32 hook fields (`resume_pc`, `last_line_pc`,
`skip_*`) and the `lineinfo`/`live_reg_top` lookups are index-typed —
see the heap-PC inventory in `p16.35-cursor-audit.md` §"Heap-PC
inventory".

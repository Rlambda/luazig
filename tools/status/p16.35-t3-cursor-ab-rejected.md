# P16.35 Cut 1 — dispatch PC as pointer cursor (PUC `savedpc`): implemented, measured, REJECTED

Cut 1 attempted to convert the dispatch-loop PC from a `usize` index into
`ctx.pc` to a `[*]const bc.Instruction` cursor `ctx.pc_cur` — the PUC
`ci->u.l.savedpc` representation. The T0.3 head decomposition promised
−2..−3 instructions per fetch: the fetch chain
`reload cur_proto spill + reload pc spill + code.ptr load + scaled load`
(4 instructions) collapses to `reload cursor spill + direct load`
(2 instructions); the tail RMW stays (`incq` → `addq $0x4`, same cost).

The implementation was COMPLETE (Stage 1: dispatch-local cursor, heap
`u.lua.pc` stays usize, ~160 sites converted), ALL functional gates were
GREEN, the instruction-level win MATERIALIZED EXACTLY AS PREDICTED — and
the A/B wall measurement REJECTED it. This artifact preserves the full
analysis so the experiment is not blindly repeated.

## 1. What was implemented (and reverted)

- `BytecodeDispatchCtx.pc: usize` → `pc_cur: [*]const bc.Instruction`;
  one canonical hot representation; heap CallFrame pc stays an index
  (Stage 1 of the two-stage plan; Stage 2 — heap pc as pointer — never
  attempted, gated on Stage 1 keeping its win).
- Helpers (both `inline fn`, file-scope in vm.zig):
  - `pcIndex(proto, cur)` — derived usize index for heap/debug consumers
    (`(cur - code.ptr) / 4`; Debug traps on underflow, mirroring the old
    `@intCast` negative-target trap).
  - `jumpCursor(cur, delta)` — signed jump arithmetic on the pointer
    (`@intFromPtr +% delta*4`; final `@intCast` traps in Debug on
    out-of-range targets, mirroring the old index-form trap).
- Site conversions (~160 code sites, all categories from
  p16.35-cursor-audit.md):
  - fetch `ctx.cur_proto.code[ctx.pc]` → `ctx.pc_cur[0]` (loop head +
    10 extracted handlers);
  - advances `ctx.pc += 1` → `ctx.pc_cur += 1` (50 plain + 35 MMBIN-skip
    + 11 condjump-skip + EXTRAARG followers);
  - MMBIN previous-instruction reads `code[ctx.pc - 1]` →
    `(ctx.pc_cur - 1)[0]` (Zig many-pointers reject literal `[-1]`);
  - jumps → `jumpCursor` (JMP, forloop/tforloop/tforprep ×2 arms,
    donextjump `off + 2`, forprep skip arms);
  - heap publishes (parkActiveFrame, hooks publish, fail sites, sync
    sites, opCall builtin pre-call) → `pcIndex(ctx.cur_proto, ctx.pc_cur)`;
  - restores (frame_loop entry, opReturn0/1 parent fast arms ×4, hooks
    block ×3) → `ctx.cur_proto.code.ptr + fr.u.lua.pc`;
  - resets (CALL fast path, opTailcall frame reuse) → `proto.code.ptr`;
  - index args (failBinaryMmbin, slowCmp, bytecodeLocalNameAt,
    debugBytecodeOperandName, parkDirectBytecodeYield ×4,
    bytecodeIndexValue/SetIndexValue, hook-yield replay compares ×2,
    skip_call_hook_pc compare) → derived `pcIndex(...)`;
  - EXTRAARG follower defensive checks (NEWTABLE, SETLIST, ERRDEFINED):
    bounds half index-derived, short-circuit `or` keeps the raw
    `pc_cur[1]` read in-bounds (Debug safety preserved exactly).
- Invariant kept: `ctx.cur_proto` and `ctx.pc_cur` always updated together
  (frame_loop entry, CALL fast path, tailcall reuse, opReturn0/1 parent
  restores) — every parkActiveFrame caller has the live pair.
- New parity gate: `tests/smoke/75_pc_cursor.lua` (9 probes: MMBIN skip +
  fallback, condjump taken/skipped, EXTRAARG followers via 300-element
  constructor, backward FOR, exact error line, hook line visibility,
  yield/resume replay mid-loop, parked-frame GC). PUC reference captured;
  passes on BOTH the index and cursor representations (representation-
  independent invariants) — KEPT after the revert.

BASE (0x10bd125):                       NEW (0x10bd136):
  mov -0xc0(%rbp),%rsi  ; proto reload    mov -0x90(%rbp),%rdx  ; cursor reload

fetch 4→2 instructions; fetch+advance 5→3. Causal, reproducible.

## 4. Wall measurement (the rejection)

perf_compare.py official gate: **FAIL** — int_arith +29.0%,
float_arith +32.6%, mixed_arith +29.8% vs baseline-p15.37
(global_arith −13.8% = the other wall mode; everything else OK).

Fewer instructions, +25-30% wall on the three tightest arith loops

minimal work between dispatches). IPC 5.51 → 4.23; cycles +25%

ld_blocks.store_forward identical (~24.5K).

### 4.1 Not the layout lottery (probed both directions)

- BASE + cold never-taken branch inside the dispatcher (`.extraarg` arm,
  shifts every subsequent handler block): int_arith 0.233-0.243,
  float 0.247, mixed 0.266 — no regression. Base is robust.
- NEW + the same probe: int_arith 0.296-0.302, float 0.305,
  mixed 0.322 — regression unchanged. New build is robust too.
- Conclusion: the wall penalty is STRUCTURAL to the cursor hot path,
  not code-placement luck (unlike P16.34 Cut 2's hash_access +12%
  layout artifact, which DID swing with perturbation).

### 4.2 Where the cycles go (perf record -F 4000)

Cycle attribution concentrates on the dispatch switch tail
(`movslq (%rcx,%rax,4); add %rcx,%rax; jmp *%rax` — byte-identical
instruction stream in both builds): base ~10% of cycles on
add+jmp*, new ~23% (13.6% add + 9.0% jmp*), plus the fetch load
1.9%→8.1%. The head itself is CHEAPER in cycles (base ~13.5% over 7
instructions vs new ~11% over 5). The penalty is diffuse per-dispatch
latency (~+2.3 c/dispatch) landing on the dependency-chain tails.

The paradox: the new fetch dependency chain is one load SHORTER
(store-forwarded cursor load → fetch) than base (fwd proto load →
code.ptr load → scaled fetch), yet the switch stalls MORE. Frontend
counters (idq.dsb_uops/idq.mite_uops) proved unreliable on this hybrid
CPU (same binary measured 191M vs 1,016M DSB uops across runs) — the
exact frontend mechanism (uop-cache/DSB way-mapping of the re-shaped
head+switch blocks, or store-forward timing of the addq→mov→load chain)
could not be isolated. What IS proven: robust, structural, ~2.3
cycles/dispatch, only visible when dispatches are back-to-back.

## 5. Decision

Per the cut's pre-registered protocol ("if Stage 1 keeps its win →
Stage 2; if pc_cur is stack-spilled anyway and the win does not
materialize in wall → REVERT with honest negative"): the cursor IS
stack-spilled (register pressure across the 68KB switch), the
instruction win did NOT survive to wall time, the official gate FAILED
→ **REVERTED**. src/ restored to HEAD be4fb0a (6290951); wall verified
restored (int_arith 0.234).

Stage 2 (heap `u.lua.pc` as pointer) was never attempted — it only
removes park-site derivations (+2 instr/park, measured ~wall-neutral
on park-heavy workloads) and cannot fix a hot-fetch-path penalty.

## 6. What a future re-attempt must do differently

- The instruction-level representation IS better (−4% instructions,
  causally proven). Any re-attempt must solve the wall paradox first:
  understand the frontend penalty (possibly via a non-hybrid perf host
  or llvm-mca), or find a form that keeps the 2-instruction fetch
  without reshaping the head/switch block boundaries.
- Candidate recorded (untested): cache `code_ptr` as a ctx field and
  keep the index pc — fetch becomes `reload code_ptr spill (plain L1
  load, written only at frame entry) + reload pc spill (forwarded) +
  scaled load` = 3 instructions, dependency depth similar to the
  cursor but block shapes closer to base. Unknown wall behavior.
- The 75_pc_cursor.lua parity gate is representation-independent and
  stays as the gate for any future PC-representation work.

# P16.35 T5 — coroutine_yield gap decomposition: lookup vs transition (2026-09-10)

**Provenance**: HEAD `a0491b3`, src/ == `be4fb0a` state (P16.35 Cut 1 reverted;
runtime identical to P16.34 final). Zig `zig build -Doptimize=ReleaseFast`
(13,455,112 B), PUC `build/lua-c/lua` (341,000 B). All counters:
`taskset -c 0 perf stat -e instructions:u`, median of 3 (C: 6 runs — bimodal).
Callgrind: valgrind 3.25.1, `--tool=callgrind`, variant D at N=20,000
(20,200 cycles incl. warmup). No production changes; research artifact only.

Reference: official counters (tools/perf/current-counters.json, measured at
6e9cd69) put coroutine_yield at zig 1,255,292,627 vs puc 507,952,478
instructions → **+1494.7 i/it** (÷500,000 iters, whole-process, no startup

## T5.1 — A/B/C/D diagnostic variants

Workload under test (tools/microbench.lua:88-97, verbatim): co body
`while true do coroutine.yield(42) end`, outer `for i=1,n do
coroutine.resume(co) end`, N//100 = 500,000 iterations, same `bench`
harness (warmup n/100 + os.clock timing). Variants in /tmp/opencode/cy_{A,B,C,D}.lua:

- **A** — exact copy (both `coroutine.resume` and `coroutine.yield` are
  per-iteration global lookups: GETTABUP `_ENV."coroutine"` + GETFIELD);
- **B** — `local resume = coroutine.resume` hoisted in the outer bench fn;
  co body unchanged;
- **C** — outer unchanged; `local yield = coroutine.yield` hoisted inside
  the co body before the `while` (executes exactly once — the loop never
  exits, so the hoist rides the single frame activation);
- **D** — both hoisted; per cycle only locals are called.

### Bytecode identity (both engines, per variant)

`./zig-out/bin/luazig --dump-bytecode` vs `./build/lua-c/luac -l`:
**opcode sequences are IDENTICAL per variant across engines** —
co body A/B: `GETTABUP, GETFIELD, LOADI, CALL, JMP`; co body C/D:
`GETTABUP, GETFIELD, MOVE, LOADI, CALL, JMP` (hoist outside the loop);
outer A/C: `FORPREP, GETTABUP, GETFIELD, GETUPVAL, CALL, FORLOOP`;
outer B/D: hoist + `FORPREP, MOVE, GETUPVAL, CALL, FORLOOP`.
Only cosmetic differences: zig reserves one extra stack slot per frame,
JMP operand encoding format, register numbering (+1 where the hoisted
local shifts the window). No engine emits extra opcodes for any variant.

### Lookup vs transition split

Per-iteration lookup cost (global pair GETTABUP+GETFIELD vs local/upval):

| engine | resume lookup (A−B) | yield lookup (A−C) | both (A−D) | per lookup |
|--------|---------------------|--------------------|------------|------------|
| zig    | 105.0 i/it          | 105.0 i/it         | 210.1 i/it | ~105       |
| puc    | 106.0 i/it          | 106.0 i/it         | 203.0 i/it | ~101.5     |

- **lookup-attributable gap** = (A−D)_zig − (A−D)_puc = 210.1 − 203.0 =
  **+7.1 i/it (0.5% of the gap)**. Zig's global-table lookup costs the
  same as PUC's (~105 vs ~101.5 i per lookup pair). The lookup path is
  NOT the problem.
- **transition-attributable gap** = gap(D) = **+1529.4 i/it (99.5%)**.
  With both engines lookup-free and byte-identical opcode sequences,
  the entire gap is resume/yield transition machinery.
- Sanity: the gap is constant across A/B/C/D (1529-1537) — the transition
  excess is fully additive and orthogonal to the lookup path. D's gap is
  pure resume/yield machinery, as predicted.
- Cross-check: B ≡ C to within 20 instructions over 505k iterations on
  zig (1,211,918,127 vs 1,211,918,107) — the two variants execute the
  same opcode multiset distributed differently, and each opcode costs
  the same in both contexts. Strong internal consistency.

Wall-clock split: gap(A) 39.5 ms − gap(D) 33.7 ms → ~85% of the WALL gap
is also transition; lookup wall difference is the remainder (zig's lookup
is more cycle-expensive than i-count suggests, but still minor).

PUC totals 787 i/cycle (matches perf 789). Of those: dispatch 200,
precall 69, **setjmp/longjmp machinery ≈ 92 i/cycle** (PUC's transition
transport — which zig does NOT pay; zig uses Zig error unions), the rest
≈ 425 is resume/poscall/xmove/checkstack value- and stack-management.

### PUC per-transition operation list (steady-state cycle)

**yield side** (co body OP_CALL → precallC → luaB_yield → lua_yieldk,
ldo.c:1006-1031): lock; `ci = L->ci`; `yieldable(L)` = ONE AND+TEST on
`nCcalls` upper bits (lstate.h); `L->status = LUA_YIELD` (1 store);
`ci->u2.nyield = n` (1 store); `ci->u.c.k = k` (1 store, NULL);
`luaD_throw(L, LUA_YIELD)` → longjmp to lua_resume's setjmp.
**Zero value copies** — yielded values are already at L->top on the co's
own stack. No frame scans: the non-yieldable-boundary fact is the nny
counter (upper 16 bits of nCcalls), O(1).

**resume side** (luaB_coresume → auxresume → lua_resume, ldo.c:966-997 +
resume() ldo.c:916-951): 2-3 status compares; `L->nCcalls =
getCcalls(from)` + limit check + increment (3 arith); setjmp (35 i);
resume(): `L->status = LUA_OK` (1 store); ci is the yield's C CallInfo —
k==NULL for coroutine.yield → skip continuation; `luaD_poscall` (pop ci,
moveresults rotates n values in place); `unroll`: ONE loop iteration —
ci = yielder's EXISTING Lua CallInfo (no frame push, no stack moves),
`luaV_finishOp` (16 i), `luaV_execute(L, ci)` re-entry on the existing
frame. Yield throws back through the setjmp; `*nresults =
L->ci->u2.nyield`; unlock. auxresume: checkstack ×2, ONE `lua_xmove`
of nres values co→main.

**GC**: PUC runs checkGC ONLY at allocation opcodes (lvm.c:1425
OP_NEWTABLE, 1631 OP_CONCAT, 1933) — **never at OP_CALL**.

**Hook check**: precallC reads `L->hookmask` directly (2 i) — the
target thread's own field; no cached-flag refresh anywhere.

### Where zig diverges (code-reading + profile)

1. **Repeated frame scans per yield** — `hasActiveBytecodeNonYieldableBoundary`
   (vm.zig:5154) walks ALL call_frames' pending_call_index; called from
   `coroutineBuiltinFastPathEligible` (out-of-line, 26 i) AND again
   inside `builtinCoroutineYield` (inlined). Plus TWO more full walks in
   builtinCoroutineYield's tail: the testc_state scan and the
   topmost-Lua-frame (suspension owner) search. ≈3 scans/yield vs PUC's
   single nCcalls AND+TEST.
2. **Repeated eligibility checks** — coroutineBuiltinFastPathEligible
   2×/cycle (69 i), each re-deriving facts (hooks, close_mode,
   yieldable, c_frame_count) that builtinCoroutine{Resume,Yield} then
   re-check themselves.
3. **Redundant state writes** — builtinCoroutineResume's ~10 defer
   blocks: 8-field VM-global error save/restore (prev_err, err_obj,
   err_has_obj, err_cframe_residue, err_source, err_line,
   err_traceback + clearErrorTraceback), protected_call_depth ++/--,
   errfunc save/restore, in_resume/capture_yield_id set/clear ×2,
   status/api_status transitions ×2, prev_thread_status save/restore,
   caller set/null. PUC's error state IS the longjmp status — nothing
   to save; status transitions are 2 stores total.
4. **Current-thread/hook refresh per switch** — switchRuntime ×2/cycle
   (157 i): park/activate copy 4 slice fields each way (bc_stack,
   bc_boxed, bc_stack_top, bc_tbc_regs) + ensureTotalCapacity(64) ×2 +
   refreshHooksCached ×2. PUC pays ZERO: each lua_State owns its stack
   permanently; "switching" is calling with the other L pointer.
5. **Result copying** — memcpy 46 i/cycle (2× setFrom in yield:
   th.yielded AND th.suspended_builtin_args hold the same values) +
   resume-tail element loop + OP_CALL post-call store loop. PUC: values
   stay on the stack until one poscall rotate + one xmove.
6. **Per-resume re-entry into runBytecodeInternal** (69 i/cycle self) —
   prologue, resume_in_place/boundary_depth derivation, yield-exit
   errdefer chain. PUC: unroll → luaV_execute on the existing ci (~26 i
   incl. finishOp).
7. **Guard chain at every builtin OP_CALL** — tryPushBytecodeProtectedCall
   (22 i incl. the defer-free check) + tryRequestBytecodeCoroutineSwitch
   (20 i) + builtinOutLen (23 i) + tryPushBytecodeDebugHook (5) +
   dispatchBytecodeHookWithCallee (4) + gcAutomaticStep (11.5) ≈ 85 i
   per call site of pure ask-then-decline, ×2 sites/cycle. PUC's OP_CALL
   (lvm.c:1720) is savepc + luaD_precall; precallC's only "guard" is the
   2-i hookmask read.

## Ranked mechanisms (provable, generic, with i/it estimates)

Ranked by (measured i/it on coroutine_yield) × genericity. Percentages
of the 1529 i/it transition gap.

### #1 — Resume-side state ceremony in builtinCoroutineResume: ~380 i/it (25%)

Measured: builtinCoroutineResume self 395 + clearErrorTraceback 14 +
re-entry excess (runBytecodeInternal'2 69 − PUC finishOp+execute-entry
~26) ≈ 452 vs PUC's whole resume entry (lua_resume 38 + resume 26 +
rawrunprotected 35 + unroll 20 + finishOp 16 = 135, of which 35 setjmp
is PUC-only transport zig doesn't pay) → **excess ≈ 350-380 i/it**.
Mechanism: VM-global error channel (self.err*) + ~10 defer blocks +
redundant status/flag transitions per resume. PUC citation: ldo.c:966-997
(lua_resume has no error-state save — the protected boundary IS the
state), ldo.c:916-951 (resume(): 1 status store + poscall + unroll).
Generic: every resume of every coroutine pays it. Fix direction:
per-thread error state (PUC model: error lives on the throwing L),
or a resume-scoped error window struct swapped by pointer instead of
8 field copies.

### #2 — Builtin OP_CALL guard chain + per-call GC check: ~230 i/it (15%)

Measured out-of-line: tryPushBytecodeProtectedCall 44 (2×22, both
early-return at vm.zig:12172) + tryRequestBytecodeCoroutineSwitch 40
(2×20, early-return at vm.zig:10452) + builtinOutLen 46 (2×23) +
gcAutomaticStep 23 (2×11.5) + debug-hook probes 18 ≈ **171 i/it**, plus
the inlined id/trampoline re-checks ≈ 60 → **~230 i/it**. PUC citation:
lvm.c:1720 (OP_CALL = savepc + precall, no GC, no guards), ldo.c:642-659
(precallC: checkstackp + prepCallInfo from the ci free list + 2-i
hookmask read), lvm.c:1425/1631/1933 (checkGC only at allocation
opcodes). Generic: EVERY builtin call in EVERY workload pays the chain
(lua_calls' `inc` is a closure, but tostring/string.format/pcall-heavy
workloads pay it too). Fix direction: hoist the id checks to the caller
(`if (id == .pcall or id == .xpcall)` and `bytecode_coroutine_trampoline_active`
before the calls), move the GC check to allocation sites (PUC parity).

### #3 — switchRuntime buffer swapping: ~157 i/it (10%, 100% zig-only)

Measured: 151 (switchRuntime self, 2 calls) + 6 (ensureTotalCapacity ×2).
PUC counterpart: **0 instructions** — per-thread stacks are permanent;
no swap, no hook-flag refresh (hookmask read directly, ldo.c:650).
Generic: every thread transition (resume in + out). Fix direction
(architectural, PUC-faithful): bc_stack/bc_boxed/bc_tbc_regs live on
Thread; dispatch dereferences current_thread — removes the swap and the
refreshHooksCached cache entirely.

### #4 — O(frames) yield-boundary derivation: ~90 i/it (6%)

Measured: hasActiveBytecodeNonYieldableBoundary 26 (out-of-line) + the
same check inlined in builtinCoroutineYield + testc_state scan +
suspension-owner scan ≈ 3 full frame walks per yield inside the 154-i
yield self. PUC citation: ldo.c:1016 (`yieldable` = one AND+TEST on
nCcalls upper bits — the nny counter IS the boundary fact). Generic:
every yield. Fix direction: O(1) active-gsub-pending counter
(inc/dec at tryStartBytecodeGsub start/completion/cancel) — the nny
counter design; the testc/owner scans can stop at the first C-frame
(c_frame_count is already O(1)).

### #5 — Value copying on the yield path: ~50 i/it (3%)

Measured: memcpy 46 (2× setFrom: th.yielded + th.suspended_builtin_args
duplicate the same values) + resume-tail copy loop. PUC citation:
ldo.c:1006-1031 (lua_yieldk copies NOTHING — values already at L->top;
one poscall rotate + one xmove total). Fix direction: yield parks a
borrowed slice (values are already in bc_stack registers at the call
site — PUC's invariant), single ownership transfer.

### Residual

~600-660 i/it of inlined OP_CALL handler staging inside dispatch self
(growCtxFrame, slice re-derivation ×3, pc/frame_cap sync, park, result
stores) vs PUC's ~25 i of inlined OP_CALL body — this overlaps #2's
inlined portions and the outs-window architecture (zig must pre-size
outs via builtinOutLen because outs is a slice; PUC's C stack IS the
outs window). Full separation needs a follow-up A/B (e.g. a
non-coroutine builtin call micro-variant).

## Cut-3 candidate

No single mechanism is overwhelmingly dominant (#1 is 25%, #2 15%, #3
10% — the gap is spread). The **Cut-3 candidate is #2 (guard-chain
hoisting + GC-check relocation)**: it is the most provably mechanical
(out-of-line symbols with exact per-call counts, zero semantic risk —
pure `if` hoisting to callers that already hold `id`), the most generic
(every builtin OP_CALL in every workload, not coroutine-specific), and
PUC-citable line-by-line (lvm.c:1720, ldo.c:642, lvm.c:1425). Expected
yield on coroutine_yield: −170..−230 i/it (11-15% of the gap); expected
side-benefit on every builtin-heavy workload. Mechanism #1 is larger
but requires an error-state architecture decision (per-thread error
state vs pointer-swapped window) and should be its own cut with a
dedicated A/B; #3 is the purest architectural divergence but is a
stack-ownership refactor touching every bc_stack access site.

### Verdict

The scan's ONLY covered fact was "a pending `.gsub` completion exists on
some frame of the active thread". Lua code can run while that pending
exists in exactly three windows:

1. repl function continuation in flight — nny already held (dup);
2. table `__index` metamethod continuation in flight — **no nny, scan-only
   (the gap)**;
3. synchronous repl/get calls — nny held around the call (dup).

No window exists where the pending `.gsub` is installed and Lua runs
without a continuation in flight: `applyBytecodePendingGsub` exits the
unit and CLEARS the pending before re-entering `advanceBytecodeGsub`, and
the synchronous loop between pushes runs no Lua (pattern matching,
interning, GC only). The scan was therefore pure duplication EXCEPT for
window 2 → fix window 2 to own the unit, then delete the scan.

Cross-thread note: the scan walked only the ACTIVE thread's frames; a
gsub repl that resumes another coroutine switches the active thread, and
the other thread's yieldability is its own nCcalls — identical semantics
under the nny unit (per-thread counter).

### The cut (T5.2)

- `tryPushBytecodeGsubTableIndex`: on a successful `__index` continuation
  push, `ccallEnter(.nonyieldable)` under the same idempotency flag
  (renamed `repl_ccall_active` → `cont_ccall_active` — it now covers both
  continuation kinds). Exit paths unchanged and generic:
  `applyBytecodePendingGsub` (completion) and `cancelBytecodePendingCall`
  (unwind, belt-and-braces) already keyed off the flag; error unwind is
  reclaimed by the owning protection's nCcalls snapshot (P16.24 model).
- **Enter-before-push refinement (pre-commit review catch)**: the unit is
  entered BEFORE the push at BOTH sites (repl + `__index`), not after.
  Reason: `pushResolvedBytecodeClosure` dispatches the child's CALL hook
  (`dispatchCalleeActivationHook`, step 5) as part of the push — in PUC
  that hook fires INSIDE the `ccall(nyci)` window (nny raised before
  precall; C callees: ldo.c:652 `luaD_hook` inside precallC, itself inside
  the ccall window; Lua callees: hook at function start inside luaV_execute,
  also inside the window). Pre-cut, the scan covered this hook window (the
  pending `.gsub` was installed at push step 2, before hook dispatch);
  entering only after a successful push would have left the hook window
  uncovered — a behavioral regression for a C hook with allow_yield that
  yields during the gsub child's CALL hook (PUC blocks it via nny). The
  restructure restores exact coverage: shared helpers
  `gsubContCcallEnter`/`gsubContCcallRollback`; rollback when the push
  declines (the synchronous fallback enters its own unit) and via `errdefer`
  when the push errors. The child's RETURN hook needs no extra handling —
  it fires in OP_RETURN while the child frame is still active, before
  `applyBytecodePendingGsub`'s exit.
- Deleted `hasActiveBytecodeNonYieldableBoundary` (10-line frame walk).
- Callers replaced by the O(1) term they already tested in parallel:
  - `coroutineBuiltinFastPathEligible` `.coroutine_yield`: `!th.yieldable()`
    alone (the duplicate scan term removed);
  - `builtinCoroutineYield`: `!th.yieldable() or (debug-hook check)`;
  - `builtinCoroutineIsyieldable`: `!t.yieldable() or (debug-hook check)`.
- No new flags/counters: the unit is the existing nCcalls upper half.

### Discovered pre-existing divergences (documented, NOT fixed here)

1. **table.sort comparator yield**: PUC blocks ("attempt to yield across a
   C-call boundary" — sort's comparator runs under the C context's
   callnoyield; empirically verified), luazig ALLOWS the suspension. Never
   covered by the gsub scan — separate mechanism (`tableSortLess` even
   special-cases a direct `.coroutine_yield` Builtin comparator, which is
   itself a name-based approximation of the missing nny unit). Needs the
   same nny-ownership treatment (sort comparator boundary) in a dedicated
   cut; same class as this cut's `__index` gap.
2. **Errored-coroutine TBC close timing**: PUC `lua_resume`'s error path
   does NOT run to-be-closed variables (no `luaD_closeprotected` in the
   unrecoverable-error branch, ldo.c:989-993); they close at
   `luaE_resetthread` (coroutine.close / thread reset). luazig closes them
   during the resume error unwind. Observable as print ordering around
   resume/close (verified with a gsub-free minimal probe). Unrelated to
   yieldability; recorded for an error-unwind architecture cut.

Both are recorded in STATUS.md as open parity items.

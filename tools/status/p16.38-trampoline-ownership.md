# P16.38 Cut 1 — T12 trampoline ownership (inventory + criterion)

HEAD at analysis: `3c68d37` (src/ == `dabfad6`). Reproducer: `/tmp/opencode/t12.lua`
(coroutine → table.sort comparator → coroutine.resume(other) → "coroutine trampoline
lost continuation" crash; PUC 5.5.0 runs it to completion).

## Root cause (confirmed by crash-site trace)

`tryRequestBytecodeCoroutineSwitch` gated ONLY on the global
`bytecode_coroutine_trampoline_active`. It cannot distinguish the trampoline's OWN
drive iteration from a NESTED HOST-RECURSIVE `runBytecodeInternal` invocation
(e.g. the sort comparator under `builtinTableSort → tableSortLess → runClosure`).
When the comparator requests a switch:

1. `tryRequestBytecodeCoroutineSwitch` sets the pending-call + switch-request +
   `caller.bytecode_inplace_suspended = true` (caller = the OUTER thread A).
2. `error.ThreadSwitch` unwinds the comparator's `runBytecodeInternal`; its errdefer
   suspension-owner check fails (boundary > 0, not the resume boundary, no testc
   C-frames) → `unwindBytecodeExecFrames` DESTROYS the comparator frame and its
   pending-call.
3. The sort's native Zig-stack state is unwound with it.
4. On the child's yield the trampoline bubbles back to A, finds A's TOP frame
   (the body frame, whose pending-call is INVALID — sort was called via the
   generic `callBuiltin` path) → `fail("coroutine trampoline lost continuation")`
   (vm.zig bubble loop).

PUC behavior: `luaB_coresume → lua_resume` from ANY depth is a nested C-stack
resume; the child runs synchronously inside the comparator and the sort state is
never at risk. The correct fallback ALREADY EXISTS in `builtinCoroutineResume`:
`if (cl.proto != null and !trampoline_active) driveTrampoline else runClosure`
(plus the unroll path's `runClosure`) — with the trampoline active, a nested
resume runs the body synchronously, preserving native state = exactly PUC.

## T1.4/T1.5 — context audit (requesting loop's thread / boundary_depth)

"drive thread" = the thread the trampoline's current drive iteration entered via
`runClosure` (all drive iterations converge on the single `runClosure` site in
`driveBytecodeCoroutineTrampoline`).

| context | how the resume is reached | requesting thread | boundary | verdict |
|---|---|---|---|---|

| gsub replacement fn | `tryStartBytecodeGsub` continuation frame, same loop | drive | 0 | chain (gsub continuation in exec_frames; repl is nny so it cannot itself yield) |

Key structural facts verified:

- On the drive thread, `boundary_depth == 0` ⟺ the requesting loop is the
  outermost `runBytecodeInternal` = the drive iteration. Any nested host-recursive
  entry has ≥ 1 resident frame below (the drive body frame or the resumed frame),
  so its boundary ≥ 1. Drive-iteration resume entries have
  `bytecode_resume_boundary == 0` for every yieldable suspension path (plain yield,
  pcall-wrapped yield, iterative __close yield — all park at boundary 0); the ONLY
  nonzero-boundary drive iteration is the cold testC-callk `finishCcall` path.
- On a NON-drive thread (sync-fallback child, c_api-resumed thread), a FRESH entry
  also has boundary 0 (its own frame stack is empty) — this is why the drive-thread
  identity check is required in addition to the boundary check.
- A stale `drive_thread` (between `prepareBytecodeCoroutineSwitch` and the next
  `runClosure` site) can never cause a false accept: the old drive thread is
  suspended (no dispatch loop running on it), and everything else is either on
  another thread (mismatch) or nested (boundary ≥ 1).

## The criterion (implemented)

```
eligible ⟺ bytecode_coroutine_trampoline_active
        ∧ requesting thread == bytecode_trampoline_drive_thread
        ∧ boundary_depth == 0
```

- `bytecode_trampoline_drive_thread: ?*Thread` — ownership recording (same class
  as `current_thread`), NOT a behavioral mode flag. Set at the drive loop's single
  `runClosure` site (every iteration converges there: fresh entry, post-switch,
  post-bubble, post-finishCcall); cleared in the trampoline's exit defer.
- A `ThreadSwitch` unwinds every Zig frame between the requesting dispatch loop and
  the trampoline's catch. That is lossless ONLY when those frames are exactly the
  trampoline's own machinery (`runClosure → runBytecodeInternal → runBytecodeDispatch`)
  — i.e. the requesting loop IS the drive iteration. The criterion identifies
  precisely that.
- Rejected resumes fall through to the EXISTING sync fallback
  (`builtinCoroutineResume` → `runClosure`, and the unroll path), which is exactly
  PUC's nested `lua_resume` (`luaB_coresume → lua_resume` under any native state).
- The eligibility decision sits BEFORE any state commit (args copy, saved-error,
  continuation alloc, pending-call, switch request, inplace-suspended) — a rejected
  request leaves zero residue.

## T1.7 — nCcalls semantics at resume entry (verified vs PUC 5.5.0)

PUC `lua_resume` (ldo.c:978-981):
```c
L->nCcalls = (from) ? getCcalls(from) : 0;   /* LOWER 16 bits only */
if (getCcalls(L) >= LUAI_MAXCCALLS) return resume_error(L, "C stack overflow", ...);
L->nCcalls++;
```
- `getCcalls` masks `0xffff` (lstate.h:107) — the parent's nny (upper bits,
  `incnny`/`decnny` ±0x10000) is NOT inherited: a child resumed from a
  non-yieldable parent IS yieldable. This is why PUC's t12 reproducer prints
  `inner-resume true inner-y` (the child yields inside the comparator's resume).
- `LUAI_MAXCCALLS` = 200 (ldo.h:63).

zig `resumeEnterC` (vm.zig) matches exactly: `co.nCcalls = from.getCcalls()` (u16
lower bits), reject at `>= Thread.LUA_MAX_C_CALLS` (200), then `+= 1`. No change
required; the nested-path child yieldability is verified by test 79 case A
(the child yields inside the comparator's synchronous resume).

## Hot-path preservation (T1.6)

The `coroutine_yield` benchmark cycle is: main → resume(A) [trampoline starts,
drive = A, boundary 0] → A's body `coroutine.yield` → park at boundary 0 →
resume(A) again [drive re-entry, `bytecode_resume_boundary == 0` → boundary 0] →
… No nested host-recursive frame ever exists on the drive thread, so the
eligibility check is two compares on a path that already loaded both fields.
Measured A (instructions:u, median-of-3, taskset -c 0): before 1,030,433,195 —
after (see STATUS): flat within noise.

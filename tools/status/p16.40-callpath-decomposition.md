### 3a. GC guard finding (root cause of the G residue)

gdb probe at the first K5 loop call: `gc_step_debt_kb = −0.075`,
`gc_count_kb = 20.38`, `gc_auto_threshold_kb = 24.36`, mode=generational,
phase=minor. The gate `if (debt > 0 and !due) return` passes EVERY call
(debt ≤ 0) while `gcAutoCycleDue` (count ≥ threshold) is false — so the
full safepoint sync + a no-op `gcAutomaticStep` entry (20 i) run per call,
and nothing ever reschedules the debt (no allocations → debt never moves).

Why the invariant `debt ≤ 0 ⟺ due` broke: `gcNoteFree` decrements
`gc_count_kb` but NOT `gc_step_debt_kb` (documented as "conservative" in
the field doc). PUC keeps the invariant tight because `luaM_realloc_`
updates GCdebt for BOTH directions (`g->GCdebt = (g->GCdebt + nsize) -
osize` — lmem.c): every free moves debt away from due exactly as the
count moves. Our one-sided accounting drifts debt to "due" while the
count says "not due", and in a no-alloc steady state the drift is
permanent — every dispatch safe point pays 48 i (safepoint sync 32 +
no-op step entry 20 − gate 12... net G=60 vs early-out ~12+site).

Cut 3's "allocation-adjacent GC guard" therefore did NOT achieve its
goal for no-alloc loops: D8 55 (P16.39) → G 60 (now, +call-site
attribution) — no real saving. The debt-init fix (32768) only delays the
drift past startup; stdlib-init frees still drive it negative before the
kernel loop starts.

### 4a. Why K5 got −121 but K6 only −56

Cut 3's four reductions all live in the GENERIC builtin path
(callBuiltin + its C-frame machinery). K6's resume/yield calls take the
P16.5b co fast path (`callCoroutineBuiltinDirect`) which bypasses
callBuiltin entirely — no snapshot discipline to save (S0/S1), no
outs-window to gate (S2), no nil-fill memset (S3), no C-frame push/pop
(zero pushBuiltinCFrame/popBuiltinCFrame/freeCFrameOwnedState in K6's
profile). K6's −56 came from the opCall-front shares only (pc-sync
removal at 18986, single-result move, guard hoisting). The GC-guard
"fix" contributed ~0 (same debt-drift bug, §3a — K6 pays D8 63).

PUC parity notes (unchanged from P16.39): PUC K6 pays luaH_getshortstr
92 (we pay 86 — parity) and setjmp/longjmp 95 (we pay ~0 — structural
win for the error-return model).

## 6. R4/R5/R6 hypothesis verdicts (pre-registered in P16.39)

- **R4.1 shrinkTo generic logic — CONFIRMED, 7–8 i/pop** (K4 R3 8, K5 P1
  7). PUC poscall is a pointer decrement (`L->ci = ci->previous`), no
  capacity logic. Real but small; folding into an R0-style architectural
  cut (frame-stack as pointer-linked PUC CallInfo chain) is the only
  PUC-faithful elimination.
- **R4.2 callstatus=0 on popped frame — CONFIRMED, 1 i** (K4 17401 xor).
  Negligible alone.
- **R4.3 parent-restore cur_upvalues load chain — CONFIRMED, 7 i/return**
  (K4 17416: func_slot → bytecode_stack → Value → .Closure.upvalues +
  spill, mis-attributed by addr2line to line 17416; verified by objdump at
  0x10d319e–0x10d31bc). PUC never re-derives upvalues on return — `cl`
  stays live in luaV_execute's frame across the call (upvals accessed via
  ci->func only at frame ENTRY). Candidate: cache upvalues in
  CallFrame.u.lua next to proto (set once at push) — removes the chain
  from every parent resume (K4 R6, K6 D2).
- **R4.4 activation stores vs PUC prepCallInfo — CONFIRMED as the K4
  call-path story**: C2+C3+C4 = 45 (guards 23 + add 8 + fields 14) vs
  PUC precall-Lua ~20 (next_ci + 5 field writes). The 25-i difference is
  the guard cascade (vararg/missing-args/capacity) that PUC pays instead
  in luaD_precall's non-fast path — but PUC's fast path (fixed-args,
  stack fits) skips them via one `cl->stackcheck`. Our pushStagedFast
  re-derives per call what PUC's CallInfo layout makes unconditional.
- **R5 active_builtin ceremony — CONFIRMED, 16 i/call** (K5 B0). No PUC
  equivalent (C functions are not registered on the VM). Serves
  error-message attribution (`__NAME__` composition) and refreshBuiltinOuts
  for re-entrant builtins. Candidate: fold into the builtin_may_refresh_outs
  gate (only re-entrant builtins need identity) — but error paths must
  keep attribution; needs a dedicated audit before cutting.
- **R6 memset status — RESOLVED by Cut 3**: nil-fill 38 → 10 (inline
  0...8 stores; memset only for >8-wide windows). No residue worth
  chasing.

## 7. Cut 2 — ranked decision (ONE production cut)

Ranked by (absolute gap × cleanliness of the PUC model):

1. **GC-debt discipline (chosen)** — make `gcNoteFree` and
   `gcCreditTreeMemory` also update `gc_step_debt_kb` (+kb, away from
   due), restoring PUC `luaM_realloc_`'s two-sided GCdebt accounting
   (lmem.c: `g->GCdebt = (g->GCdebt + nsize) - osize`) and the invariant
   `debt ≤ 0 ⟺ cycle due` that `condGcFromDispatch`'s gate was designed
   around. In no-alloc steady state the gate then early-outs (~12 i)
   instead of paying the safepoint sync + no-op step entry.
   - Expected: K5 G 60 → ~19 (site 7 + gate 12) = **−41 i/it (709 → ~668,
     2.82x → 2.66x)**; K6 D8 63 → ~22 = **−41 i/it (2028 → ~1987)**;
     K4 unchanged (no builtin calls). Alloc-heavy workloads: the gate
     fires exactly when PUC's would (debt tracks count two-sided).
   - PUC model: exact — this IS PUC's accounting, one-sided debt was our
     deviation (documented "conservative" in the gc_step_debt_kb field
     doc, now shown to cost 48 i/call in no-alloc loops).
   - Pre-registered rejection rules: (a) any matrix/smoke/api580
     regression → reject; (b) perf_compare geomean > +1% (the gcNoteFree
     add sits on the sweep hot path — one f64 add per freed object) →
     reject; (c) gc/coroutine upstream suites must stay green (debt
     semantics shift automatic-cycle timing toward PUC's —
     `collectgarbage("count")`/step tests are the canary); (d) K5/K6
     callgrind must show the gate early-out (G/D8 drop ≥ 30) — if the
     debt still drifts (another one-sided writer found), fix that writer
     or reject.
2. **C-frame lifecycle cost for non-reentrant builtins** (K5 F3+P0+P1 ≈
   135 vs PUC precallC+poscall 71). PUC-faithful direction: slim the C
   CallFrame push to PUC's precallC field set and make pop a pointer
   move (ties into the frame-stack-as-CallInfo-chain architecture).
   Bigger blast radius (FrameStack invariants, GC scanning, yield park);
   deferred until the GC-debt cut lands.
3. **R4.3 upvalues cache in CallFrame.u.lua** (−7 i/return on K4, −7 on
   K6 D2 per entry). Small, clean, but touches CallFrame layout (88 B —
   field must fit CFrameState too); bundle with the next layout change,
   not alone.
4. **R0 gate cascade consolidation** (K4's biggest single item, 66 i).
   Requires encoding "plain Lua child of Lua parent" at push time
   (PUC-style callstatus bits) — architectural, K4-focused; K4 is the
   SMALLEST absolute gap (171), so ranked last despite cleanliness.

Decision: implement cut 1 (GC-debt discipline) as P16.40 Cut 2.

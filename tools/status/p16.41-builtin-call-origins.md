## 3. Frame classes that never reach either push (unchanged)

- `collectgarbage`, `string_sub` (`builtinNeedsCFrame == false`): frameless
  (documented Cut 1 deviation, hot-path guard).
- coroutine.resume/yield `co_fast_path` (`callCoroutineBuiltinDirect`): no
  frame (P16.5b guards: no hooks, no continuations, no close mode).
- divert-bound fast paths (pcall/xpcall `tryPushBytecodeProtectedCall`,
  pairs `__pairs`, gsub, coroutine switch): replaced by bytecode
  continuations before the generic path; hook keeps the legacy caller-frame
  identity (documented P15.83r sub-deviation).

## 4. Pre-existing hole noticed (NOT this cut's scope)

`opTforcall` skips `callBuiltin` entirely when `builtinNeedsCFrame(id)` is
false (a frameless builtin as for-iterator — e.g. `for x in string.sub`):
outs stay Nil-filled and the loop sees no values, while PUC would call the C
function. Nonsensical shape, no suite covers it; recorded for the semantic
backlog.

## 5. Consumers audited for the view model (func_slot semantics)

- GC: per-frame `bc_stack[func_slot]` mark — view slot holds the real callee
  (also inside the caller's window) ✓; `shrinkBcStack` skips C frames ✓.
- debug: `getinfo().func`, `getFuncNameForFrame`, traceback walks — all
  index-based, same Value at the slot ✓. `suspendedCWindow`: plain builtin
  yields → empty window in both models ✓.
- Result movement (opCall): outs window is `regs[a+1+nargs..]` (the CALL
  window), results copied to `regs[a]` — never derived from the synthetic
  slot; dst/nresults-padding/multret reg_top are all a-relative ✓.
- `bytecode_stack_top` restores for a C-frame CALLER (popBuiltinCFrame,
  poscallCFrame, popBytecodeExecFrame, discardCFrame): staged frames restore
  `func_slot(+1)`; **view frames must restore the below Lua frame's window
  top** — the only arithmetic that changes (new CIST_VIEW bit).
- pcallk `funcidx` (builtinPcall on a view frame): bc-stack-relative in both
  models (staged: synthetic+1; view: real callee+1 — closer to PUC's
  `savestack(L, c.func)`); consumer guards `funcidx <= cur_c_stack.len`
  behave identically.

## 6. Cut 3 implementation record (2026-09-12)

**Model** (PUC ldo.c precallC: `ci->func = func` — the callee slot is IN the
caller's window, never a staged duplicate above it):

- `CIST_VIEW` bit (`1 << 28`) + `isView()`/`setView()` on CallFrame.
- `pushBuiltinCFrameAt(func_slot)` — view push: NO stack write, NO top
  advance, NO growth check (the slot already exists in the caller's
  window); only failure is `call_frames.addOne` OOM. Shares field init
  with the staged push via `initBuiltinCFrame`.
- `pushBuiltinCFrame` (staged) — unchanged semantics, now shares
  `initBuiltinCFrame`.
- `popBuiltinCFrame` — view frame: top = below Lua frame's window top
  (`below.frameBase() + below.u.lua.frame_cap`; invariant: view frames
  are pushed only from bytecode dispatch, so the frame below is always
  the Lua frame whose OP_CALL/OP_TAILCALL/OP_TFORCALL is executing);
  staged frame: `func_slot` as before.
- `restoreTopAtFrame(frames, caller_idx)` helper: restores
  `bytecode_stack_top` for a caller by frame class (C staged →
  `func_slot`; view → below-Lua window top; Lua → its own window top).
  Used by `poscallCFrame`, `discardCFrame`, `popBytecodeExecFrame` —
  covers the sort-comparator/metamethod hot path (Lua frame returning
  with a view C frame below it).
- `callBuiltin(id, args, outs, origin: BuiltinCallOrigin)` —
  `enum { bytecode_window, host }`; replaces the
  `builtin_cframe_pre_pushed` global (deleted). `.host` pushes staged
  (needsCFrame-gated); `.bytecode_window` never pushes (the dispatch
  site pushed the view frame) and never grows.
- Dispatch sites: `opCall`/`opTailcall` push the view frame for EVERY
  C-frame builtin (not just hook-deferred) at `ctx.base + a`;
  `opTforcall` at `ctx.base + a + 4` (iterator at R[A+4]). The C
  activation hook fires on the view frame; stack-base re-derive moved
  inside the hook block (the view push cannot move the base; only the
  sync hook body can). Frameless builtins (collectgarbage/string_sub)
  pass `.host` — the staged arm is needsCFrame-gated, so nothing is
  pushed either way (Cut 1 deviation, unchanged).

## 7. Pre-existing divergences discovered while writing test 82 (NOT
## regressions; verified at HEAD `2d9cc8c` via stash)

1. **pcall-caller arg-error naming**: `pcall(math.abs, "x")` → PUC
   `"bad argument #1 to 'math.abs' (…)"` (no chunk location; name
   fallback for a C caller); luazig → `"…:LINE: bad argument #1 to
   'abs' (…)"` (the pcall divert has no real C frame, so luaL_where and
   the name resolve from the Lua caller). Frame-model-adjacent (the
   divert's missing pcall C frame), separate from Cut 3.
2. **TFORCALL callee hook naming**: a C iterator called via OP_TFORCALL
   is named `"for iterator"` by PUC (funcnamefromcall reads the caller's
   instruction); luazig names it `"next"` (the builtin's registered
   global name). The hook itself fires on the (view) C frame correctly.
3. **string.rep arg-error text**: luazig `"string.rep expects integer n"`
   vs PUC `"bad argument #2 to 'rep' (number expected, got string)"`
   (string-library message format, unrelated to frames).

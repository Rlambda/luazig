# P16.42 T2 — cstack.lua Debug segfault ("chain of 'coroutine.close'"): classified, DEFERRED

Date: 2026-09-12. HEAD at investigation: 0728e37 (P16.42 Cut 1).

## Symptom

`cstack.lua --testc` in **Debug** segfaults in the "chain of
'coroutine.close'" test (cstack.lua:87-110). **ReleaseFast passes**
(count=200, matching the LUA_MAX_C_CALLS=200 limit; PUC errors at count=197
— the already-documented pre-existing count-diff, see P16.41 notes).

## Reproduction matrix (probe /tmp/opencode/p42_cstack_N.lua, N-deep close chain)

| N     | luazig Debug      | luazig ReleaseFast | PUC lua            |
|-------|-------------------|--------------------|--------------------|
| 100   | pass (count=100)  | pass               | pass               |
| 200   | **SEGFAULT**      | pass (count=200)   | error at count=197 |
| 300   | **SEGFAULT**      | pass (count=200)   | error at count=197 |
| 1000  | **SEGFAULT**      | pass (count=200)   | error at count=197 |

Crash depth is constant **~198** across `ulimit -s` 2048/4096/8192/16384.

## Root cause: genuine host-stack exhaustion (Debug-only frame-size artifact)

gdb: fault is the Zig stack probe (`test %esp,-0x1000(%rsp)`) at
`builtinCoroutineResume` entry; rsp sits at the bottom of the 16 MB `[stack]`
VMA. The environment enforces a **fixed ~16 MB main-thread stack ceiling
regardless of rlimit** (verified with a dedicated recursive Zig probe:
16 MB recursion completes at `ulimit -s 2048`, 20 MB crashes; `ulimit` is
not honored in this container).

Recursion cycle per close level — 8 Zig frames:

```
builtinCoroutineClose (vm.zig:23805 transport path; taken because suspended
  coroutines carry trace_yields > 0, incremented at vm.zig:11446/23504)
→ builtinCoroutineResume (22640/23243)
→ runClosure → runBytecodeInternal → runBytecodeDispatch
→ opCall → callBuiltin → callBuiltinSwitch
→ builtinCoroutineClose (next level)
```

Debug frame sizes (gdb CFA deltas + objdump `sub rsp`):

| frame                 | bytes  |
|-----------------------|--------|
| runBytecodeDispatch   | ~44.9K (dynamic `sub %r10,%rsp`) |
| builtinCoroutineResume| ~16.9K |
| opCall                | ~8.6K  |
| callBuiltinSwitch     | ~5.1K  |
| runBytecodeInternal   | ~4.5K  |
| callBuiltin           | ~2.6K  |
| builtinCoroutineClose | ~1.2K  |
| runClosure            | ~0.4K  |
| **total per level**   | **~84.2K** |

~84.2 KB × 200 semantic limit ≈ 16.8 MB > 16 MB ceiling → dies at depth 198,
just under the correct limit.

## Why the task's fix condition ("make iterative where PUC is") does not apply

PUC **also recurses in C here**: `lua_closethread → luaD_closeprotected →
callclosemethod → luaD_callnoyield → luaD_call → luaV_execute → precallC`
per close level, bounded by `nCcalls`/LUAI_MAXCCALLS=200 — PUC is NOT
iterative in this path. PUC survives because its per-level C frames are
~1 KB, not ~84 KB. cstack.lua's own header documents this crash class
("ensure a larger stack for the program").

## Classification

- **Semantics: correct.** The nCcalls counter fires at the right semantic
  limit; ReleaseFast behavior matches PUC modulo the documented count-diff
  (200 vs 197).
- **Class: host-stack exhaustion, Debug-codegen frame-size artifact.**
  Not a memory-safety bug, not a semantics bug.
- **Decision: DEFER.** Real fixes would be either (a) non-PUC iterative
  rework of the close/resume transport — a deviation from PUC architecture
  with real complexity cost, or (b) fighting Debug-codegen frame sizes on
  the hottest dispatch path (runBytecodeDispatch's dynamic stack frame is
  the whale) with likely ReleaseFast perf side effects. Neither is
  justified for a Debug-only artifact whose semantics are already correct.

## If revisited

Cheapest honest mitigation if Debug CI stability ever demands it: raise the
host stack for the main thread at startup (spawn interpreter on a thread
with a large stack) — an environment fix, not a VM fix. The frame-size
table above is the input for any such decision.
